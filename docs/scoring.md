# 评分模型

## 两个不同的问题

| 指标 | 问题 | 进不进评分 |
| --- | --- | --- |
| `difficulty` | 这次的活有多重？ | **不进**。runner 不该因为被派重活而扣分 |
| `job_score` | 这一次执行得好不好？ | 单次任务质量 |
| `RPS` | 这台 runner 整体跑得怎么样？ | 综合评分 |

## 四条腿

所有腿都在 0–100。

### 可靠 reliability

```
成功 100 · 取消/跳过 35 · 失败 0 · 未完成 → 无此腿
```

### 速度 speed

先算比值，再取对数，目的是让「快一倍」和「慢一倍」对称：

```
ratio      = 同名任务历史中位耗时 / 本次耗时
speed_index = clamp(100 × ratio, 0, 300)          # 100 = 中位
speed_score = clamp(50 + 40·log2(clamp(ratio, 0.25, 4)), 0, 100)
```

- ratio = 1（正好中位）→ 50
- ratio = 2（快一倍）→ 90
- ratio = 0.5（慢一倍）→ 10

`log2` 的意义：从 100s 优化到 50s 与从 20s 优化到 10s，收益相同。

**中位数的取法**：优先同名任务；同名样本 < 3 时退回全局中位。这样冷启动阶段不会用一两个样本乱打分，也不会把「Verify and package 天生要 3 分钟」算成慢。

### 效率 efficiency

```
busy        = clamp(worker 子进程累计耗时 / 墙钟耗时, 0, 1.5)
efficiency  = busy/1.5 × 40
            + min(40, 40 × 中位/本次)      # 越快越高
            + (成功 ? 20 : 0)
```

`busy` 接近 1 说明 runner 一直在干活而不是空转；超过 1 是并行步骤，因此上限给到 1.5。

### 稳定 stability

```
penalty  = 错误行×6 + 失败步骤×10 + 非 0 退出码×4 + (失败 ? 15 : 0)
stability = clamp(100 - penalty)
```

条件跳过（`Skipped`）**不算**失败步骤。

## 合成

```
RPS       = 可靠·0.40 + 速度·0.25 + 效率·0.20 + 稳定·0.15
job_score = 可靠·0.35 + 速度·0.25 + 效率·0.20 + 稳定·0.20
```

单次任务给稳定更高权重：一次执行的「干净程度」比长期统计里更重要。

**缺腿自动重新归一化**：worker 日志被轮转掉的任务没有 speed/efficiency/stability，那就只用可靠性评分（等于可靠值）。这是刻意的——宁可基于更少的证据打分，也不要丢掉整条历史。

## 等级

| 等级 | 分数 |
| --- | --- |
| S | ≥ 90 |
| A | ≥ 80 |
| B | ≥ 70 |
| C | ≥ 60 |
| D | ≥ 50 |
| F | < 50 |

## 难度（不进评分）

```
difficulty = log2(1 + 耗时秒)      × 5.2
           + 步骤数                 × 0.9
           + log2(1 + 子进程耗时秒)  × 2.8
           + log2(1 + 日志KB)        × 1.2
           + 错误行                  × 0.35
           + (失败 ? 10 : 0)
```

夹到 0–100。用途是**解释**评分：`Verify and package` 的 RPS 低，是因为难度高导致偶尔超时，还是因为 runner 真的不稳？把两者并排看就分得清。

## 趋势图 = 滚动 RPS

横轴是任务完成时间。第 i 个点 = 第 `i-N+1 .. i` 次任务（默认 N=6）的 RPS。

所以曲线回答的是「**最近这段时间这台 runner 表现如何**」，而不是把三个不同量纲的指标硬叠在一张图上。

- 起步阶段窗口没满（n<6），分数波动大是正常的；
- 一个失败会被带到后面 5 个点上，然后滑出窗口；
- 每台 runner 也各有一条自己的滚动线，默认不勾选。
